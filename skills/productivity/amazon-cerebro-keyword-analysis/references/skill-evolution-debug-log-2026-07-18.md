# Skill Evolution Debug Log · 2026-07-18 (B0H35TQ81F case)

> **这份文档是给"如何根据用户反馈升级 skill"的人看的 case study，不是给跑 Cerebro 的人看的。** 跑 Cerebro 请看主 SKILL.md。

## 背景

2026-07-18，bailing 跑 B0H35TQ81F 的 Cerebro 反查。skill 当时是 v2 版本，方法论基于 "4 级广告分级 (S/A/B/C/D) + 大/中/小流量分层 + IQ 优先级公式"。

bailing 看了报告后**直接说"结论和事实有严重偏差"**，并给了一条**截图证明**：他用红线把头部词标出来，理由是"对于新品来说很难成交，因为这些都是很不相关的关键词"。

然后他给了 **4 条新规则**：

1. **相关性过滤**：竞品表现得分 8–10 高 / 6–8 中 / 4–6 弱 / <4 不相关
2. **流量等级 S/A/B/C/D**：≥50K=S / 10K–50K=A / 5K–10K=B / 1K–5K=C / <1K=D
3. **白牌准入难度**（ABA 转化份额）：>70% 极激烈 / 50–70% 很高 / 30–50% 高 / 15–30% 一般 / <15% 友好
4. **竞品数蓝海度**：≥1万 极激烈 / ≥5千 激烈 / 1000–5000 一般 / 500–1000 温和 / <500 蓝海

**最后一句判断（关键）**："你之前推荐行动拓词抢首，这一些是有问题的。拓词抢首一般选择竞争不是很激烈的市场，然后选择一些 B、C 级词，甚至 D 级词。后期才选择 A 级词，甚至 S 级词。"

## Debug 过程（4 步升级）

### Step 1: 我跑出来的 v2 结果是怎样的

- **TOP 30 priority** 几乎全部是品牌词：`carotone cream` / `strivectin` / `gopure` / `get dreamy overnight toning whip` / `noor wonder lift cream` / `medicube collagen jelly cream` ...
- **看似合理**（品牌词 IQ 高），但**完全不能投**（品牌词 = 不能抢的）
- **优先级公式 bug**：`priority = IQ*0.4 + CPR*0.3 + comp_score*0.3` 没有"广告级"加权

### Step 2: bailing 反馈后第一次修复

我加了"广告级加权"（C 级=0, S 级×1.5, A×1.2, B×1.0, D×0.3），TOP 30 变成全部 S 级长尾词。但**这还不够** — 整个方法论还是错的。

### Step 3: 接收 4 条新规则 → 重构

**核心范式转变**：

| v2 范式 | v3 范式 |
|---|---|
| 单维度 priority 排序 | 4 维度评估 + 推荐行动反推 |
| 流量大 = 值得打 | 流量大 = 巨头护城河 |
| 广告分级 = 推荐动作 | 流量等级 ≠ 广告分级（**命名冲突**） |
| 没有相关性过滤 | comp_perf 是**第一道闸门** |

**修复中踩的坑**：

1. 第一次执行时把"ROOT 库"放太宽（把 body/face/eye 也算 root），结果 73% 都是 ROOT — **立即调整 CORE_ROOTS 列表**
2. Priority 公式第一次没考虑"广告等级"权重，导致品牌词霸榜 — **改为 4 维度评估系统，priority 公式直接废弃**
3. v3 CSV 列数从 20 改到 17，**老用户读老 CSV 会有列错位** — 必须在 SKILL.md 顶部加 v2→v3 升级变更日志

### Step 4: 跑新案例 B0CGB215HR 时又发现新模式

bailing 发了**新一份 Cerebro 报告**（8,294 行 vs 之前 4,115 行），我**最初误读为单 ASIN 反查**。bailing 解释后我才明白：

> "这一份表格不是一个 ASIN 的它背后关键词，而是多个 ASIN 它们整体报表的混起来的。"

**comp_perf 列的语义完全不同**：
- 单 ASIN 模式 = 1 个 ASIN 在该词的表现
- 多 ASIN 模式 = 多个竞品 ASIN 在该词的**综合打分**

**结论**：skill 必须**支持两种模式**，不能假设只有一种。这又是一个 v3.1 的扩展。

## 教训（写给未来的 agent）

### TL-1: 用户给"截图 + 几条规则 + 一句判断"时，别只字面执行

bailing 给的 4 条规则字面是"加 4 个阈值"，但他的**最后一句判断**才是核心——"流量大 ≠ 推荐打"。**只加 4 个阈值不够，必须重构推荐行动的反推逻辑**。

### TL-2: 报告里出现"品牌词霸榜"是 methodology bug 的强信号

如果 priority 公式跑出来 TOP 30 全是品牌词（C 否定类），**说明公式有 bug，不是数据有问题**。修复方向是给"广告级"加 0 系数 + 反向加权。

### TL-3: 流量等级 S/A/B/C/D 和 广告分级 S/A/B/C/D 命名冲突

v2 用同一套字母表示**两件事**（流量 + 广告），导致"流量大 = 广告要打"这种隐含 bias。v3 必须**拆开**：
- 流量等级 S/A/B/C/D（中性事实）
- 推荐行动 `捡漏 / 主推 / 拓词 / 防守 / 观察 / 否定`（决策动作）

### TL-4: 多 ASIN 综合反查是真实存在的 Cerebro 模式

bailing 的 3 ASIN 综合报告（B0CGB215HR + B07SZ5CLN9 + B0F2J966QL）有 8,294 行 34 列，跟单 ASIN 的 35 列不同。**必须 schema-aware**：
- 列数 35 = 单 ASIN 模式（最后 3 列是排名数字）
- 列数 34 = 多 ASIN 模式（最后 2 列是完整 ASIN 列）

### TL-5: SKILL.md 的升级变更日志是"防御工事"

每次重大重构后，在 SKILL.md 顶部加一张"v2 → v3 变更对比表"。这样未来 agent 一打开就能看到：
- 哪些规则**已废止**（避免误用）
- 哪些是**当前正确**的
- 升级影响（哪些老数据需要重跑）

**没有变更日志，agent 容易照着 v2 的旧思路跑 v3 的数据 → 重新踩坑。**
